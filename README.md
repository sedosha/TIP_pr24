# Цель занятия

## CI и CD

**CI (Continuous Integration)** – это практика автоматической проверки каждого изменения в репозитории. После push или pull request система автоматически запускает тесты, проверяет сборку и уведомляет о результате. Это предотвращает интеграционные проблемы и гарантирует, что код не сломан.

**CD (Continuous Delivery / Deployment)** – это следующий этап: автоматическая упаковка приложения (например, в Docker-образ), публикация в реестре и, при необходимости, развёртывание на сервере. В рамках работы реализована CI и базовая часть CD (сборка Docker-образа).

## Выбранная платформа и структура pipeline

В качестве CI/CD-системы выбран **GitHub Actions** – встроенный инструмент GitHub, удобный для Go-проектов.

Pipeline описан в файле `.github/workflows/ci.yml` и состоит из двух job:

| Job | Назначение |
|-----|-------------|
| `test-and-build` | Установка Go, загрузка зависимостей, запуск тестов, сборка бинарного файла |
| `docker-build` | Сборка Docker-образа на основе multi-stage Dockerfile (зависит от успеха первого job) |

## Полный YAML-файл pipeline

```yaml
name: CI Pipeline

on:
  push:
    branches: [ "main", "master" ]
  pull_request:
    branches: [ "main", "master" ]

jobs:
  test-and-build:
    runs-on: ubuntu-latest

    defaults:
      run:
        working-directory: ./services/tasks

    steps:
      - name: Checkout repository
        uses: actions/checkout@v4

      - name: Setup Go
        uses: actions/setup-go@v5
        with:
          go-version: '1.23'

      - name: Show Go version
        run: go version

      - name: Download dependencies
        run: go mod tidy

      - name: Run tests
        run: go test ./...

      - name: Build application
        run: go build ./...

  docker-build:
    runs-on: ubuntu-latest
    needs: test-and-build

    steps:
      - name: Checkout repository
        uses: actions/checkout@v4

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Build Docker image
        run: |
          cd ./services/tasks
          docker build -t techip-tasks:${{ github.sha }} .
```

## Пояснение шагов pipeline

- **Checkout repository** – загружает код репозитория в виртуальную машину CI.
- **Setup Go** – устанавливает нужную версию Go (1.23).
- **Show Go version** – проверяет, что версия установлена корректно.
- **Download dependencies** – выполняет `go mod tidy` для загрузки зависимостей и создания `go.sum` (если его нет).
- **Run tests** – запускает все тесты в пакетах `./...`. В проекте добавлен минимальный тест для эндпоинта `/health`.
- **Build application** – выполняет `go build ./...` для проверки компиляции.
- **Set up Docker Buildx** – подготавливает окружение для сборки Docker-образов.
- **Build Docker image** – собирает образ с тегом, содержащим SHA коммита (например, `techip-tasks:a1b2c3d`).

## Формирование тега Docker-образа

В качестве тега используется **SHA коммита** (`${{ github.sha }}`). Это позволяет однозначно связать собранный образ с исходным кодом. Такой подход удобен для отслеживания версий и отката при необходимости. Дополнительно можно добавить тег `latest` для самого свежего образа.

## Хранение секретов

Токены, пароли и SSH-ключи **не должны храниться в репозитории или в YAML-файлах**. В GitHub Actions они размещаются в **Settings → Secrets and variables → Actions**. В нашем pipeline секреты не использовались (образ собирался без публикации), но при необходимости публикации в registry потребуется создать секреты (`REGISTRY_USERNAME`, `REGISTRY_PASSWORD` или `GHCR_PAT`).

## Контрольные вопросы
1. **Чем CI отличается от CD?** CI (Continuous Integration) — это практика автоматической проверки кода после каждого изменения: запуск тестов, сборка, проверка стиля. CD может означать Continuous Delivery, когда результат CI готов к развёртыванию, но деплой требует ручного подтверждения, либо Continuous Deployment, когда каждое успешное изменение автоматически попадает на сервер. Таким образом, CI отвечает за корректность кода и сборку, а CD — за доставку собранного артефакта в целевую среду.

2. **Почему pipeline должен запускать тесты?** Тесты — это первая линия защиты от регрессий: они обнаруживают ошибки до того, как код попадёт в основную ветку или в production. Автоматический запуск тестов в pipeline освобождает разработчика от ручного прогона и исключает ситуацию «забыл запустить тесты». Если тесты падают, пайплайн сигнализирует об этом сразу, и команда может исправить проблему, не тратя время на отладку в уже интегрированном коде.

3. **Зачем нужен автоматический build?** Автоматическая сборка гарантирует, что проект компилируется в окружении, отличном от машины разработчика, и выявляет скрытые проблемы с зависимостями или конфигурацией. Она также даёт уверенность, что код действительно можно превратить в работающий артефакт (бинарный файл, Docker-образ). Без автоматической сборки легко получить ситуацию, когда у одного разработчика всё работает, а у другого — нет, из-за различий в инструментах или версиях библиотек.

4. **Почему важно собирать Docker-образ в CI, а не только локально?** Локальная сборка зависит от текущего состояния машины и может быть невоспроизводима на другом компьютере. CI гарантирует, что образ всегда собирается из чистого окружения по одному и тому же сценарию, что исключает ошибки «у меня работало». Кроме того, собранный в CI образ можно сразу опубликовать в реестре и использовать для деплоя автоматически, без ручного вмешательства.

5. **Что такое CI secrets?** CI secrets — это чувствительные данные (токены, пароли, ключи SSH), которые безопасно хранятся в настройках CI-платформы, но не попадают в репозиторий. В GitHub Actions secrets задаются через интерфейс Settings → Secrets and variables → Actions. Внутри пайплайна на них можно ссылаться как на переменные окружения или аргументы команд, но из внешнего доступа они защищены и не отображаются в логах.

6. **Почему нельзя хранить токены и SSH-ключи в репозитории?** Любой, кто имеет доступ к репозиторию, сможет прочитать эти данные, даже если они лежат в закрытых ветках или истории коммитов. Токены и ключи дают доступ к внешним ресурсам (реестры, серверы, облачные API), и их утечка приводит к компрометации инфраструктуры. CI secrets решают эту проблему, отделяя хранение секретов от кода и ограничивая доступ только к выполняемым пайплайнам.

7. **Для чего нужен тег Docker-образа?** Тег — это идентификатор версии образа, который позволяет отличать сборки друг от друга. В CI в качестве тега удобно использовать SHA коммита, чтобы однозначно связать образ с исходным кодом, который его породил. Тег также может быть `latest` для обозначения самой свежей версии; для откатов или канареечных развёртываний используются конкретные версии (например, `0.1.2` или `a1b2c3d`).

8. **Что делает job docker-build?** Job `docker-build` отвечает за сборку Docker-образа на основе Dockerfile, который находится в репозитории. Обычно этот этап выполняется после успешного прохождения тестов и сборки исходного кода, чтобы зря не тратить ресурсы на образа, которые заведомо не пройдут проверку. В рамках job также можно навесить теги, запушить образ в реестр и, при необходимости, запустить сканирование уязвимостей.

9. **Почему в multi-service проекте важен working-directory?** В multi-service проекте несколько сервисов лежат в поддиректориях (например, `services/auth`, `services/tasks`). Без указания `working-directory` CI будет выполнять команды в корне репозитория, что может привести к сборке не того сервиса или к ошибкам «файл не найден». Установка `working-directory: ./services/tasks` гарантирует, что все шаги (сборка, тесты, Docker build) выполняются в правильном контексте, как если бы мы зашли внутрь папки сервиса.

10. **Какие риски возникают при полностью автоматическом деплое?** Полный автоматический деплой означает, что каждое успешное изменение немедленно попадает в production, что повышает вероятность доставки бага или регрессии конечным пользователям. Если автоматически не настроены дополнительные проверки (канареечные развёртывания, smoke-тесты после деплоя, откат по таймауту), то сбой может остаться незамеченным до появления жалоб. Также при полной автоматизации сложнее контролировать синхронизацию релизов между несколькими сервисами, что может привести к несовместимости версий.
